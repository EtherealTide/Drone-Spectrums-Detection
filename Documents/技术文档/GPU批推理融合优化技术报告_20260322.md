# 无线无人机检测系统技术报告（2026-03-26）

## 1. 报告目的

本文档详细记录围绕“数据访问与纯GPU检测链路深度重构”的全部技术演进，主要目标包括：
- 废除原有的数据处理进程，实现通信接收与数据处理的轻量级融合。
- 引入无锁（Lock-Free）与零拷贝（Zero-Copy）的纯GPU计算环境，打造极致高吞吐的推理流水线。
- 彻底摒弃由于串行控制与低效通道转换带来的瓶颈，保证从模型加速到数据管道的全面优化。
- 记录改造过程中遇到的张量布局异常、越界拷贝报错排查过程与解决方案。

---

## 2. 改造前架构痛点与基线局限

### 2.1 早期 CPU 瓶颈与分层负担
在最初版本中，数据处理阶段的关键计算（全局归一化、色彩映射、图像组装等）完全由 CPU 承担。在极高质量（如全长 10240 甚至 20480）频谱图的压力下，CPU 计算成为极高单帧时延的来源，不仅占用过高，还直接导致了后续推理链路饥饿。

### 2.2 跨设备通信与序列化开销
在初步尝试将其引入 GPU 后，架构依旧面临严峻的 IPC (进程间通信) 开销：
1. 网络通信进程使用 multiprocessing.Queue 频繁序列化/反序列化 1D numpy 数组进行进程间派发。
2. 即使引入了 Numpy 环形缓冲，中间生成的重卷图像仍需要在 Python 对象与指针间来回跳转，大量时间浪费在 Python C-API 的锁竞争和序列化上。
3. data_process 和 Algorithms 两套并存的耦合结构不仅链路冗长且难以观测真正的吞吐极限。

### 2.3 YOLO并行瓶颈及通道一致性
旧版本针对通道排序执行了极其损耗性能的 	orch.flip(..., [-1])，并且因为使用 best.pt 原始文件和扫描控制器框架，YOLO一直处于 =1$ 的串行检测状态下，完全无法发挥最新一代显卡的阵列算力。

## 3. 核心改造内容 (全新架构实现)

### 3.1 跨进程模型重构：废除 data_process.py
针对以上问题，系统彻底推翻了“接收 -> 处理 -> 算法 -> UI”的链式派发逻辑，全面重构为如下两大主要进程模块：

#### 3.1.1 数据接入与 DSP 轻量化层（
eceiver.py）
- **功能合并**：原有的网络数据通信接管了原本属于 data_process 的 1D 数字信号处理（DSP）步骤（降噪、基底滤波、数组长度修补等）。
- **零 IPC 序列化下发**：移除了原本厚重的 fft_data_q 队列。新的接收器获取完整帧并完成轻量处理后，直接覆盖写入带有高度限制的全新共享内存结构 $shm_waterfall 中。
- **无锁状态同步**：引入原子整型 mp.Value('i')（
ing_write_idx, 
ing_count），由接收器单向写入状态，供推理端监控，免去了互斥锁争抢。

#### 3.1.2 纯 GPU 推理引擎层（inference_engine.py）
- **极速状态嗅探**：通过约200次/秒的非阻塞自旋操作监控 
ing_write_idx 参数更新，避免了 Queue.get() 的无谓阻塞。
- **并入 YOLO 检测逻辑**：将 Algorithms 集成于此类下，共享同一 CUDA Stream/Context 周期。

### 3.2 张量内存布局极致优化 (HWC 到 CHW 一步到位)
废弃了原先反复冗余的通道拼接与逐图重构开销：
- **生成原生 RGB 的 JET 色彩表**：在初始化时，通过 CPU的OpenCV将 COLORMAP_JET 的 BGR 预先逆转为 RGB 的 LUT，存放至 GPU，省去每张图对通道维度进行 	orch.flip 的昂贵消耗。
- **View 与 Permute 重排列**：从重塑整个瀑布大图阶段，直接利用 Tensor 的内存连续化机制构建符合推理端期望的 NCHW 四维张量：

```python
  batched_tensor = (
      color_tensor[:, :usable_width, :]
      .contiguous()
      .view(self.waterfall_height, window_count, window_w, 3)
      .permute(1, 0, 2, 3)  # -> [B, H, W, C] (PyTorch permute -> C维在最后?) 调整为 -> [B, 3, H, W]
      .contiguous()
  )
```
  直接以零系统拷贝的方式转换出批量四维输入。仅仅在确定需要送向 UI 层的那单一窗口图片，采用 .cpu().numpy() 并回退 cv2.cvtColor 为 BGR 刷新前端页面。

### 3.3 YOLO 并行批推理与底层引擎革新
完全弃用了旧版扫描控制器的时时滚动截取形式，直接启用 TensorRT 以 Batch=16 的一次性矩阵算力通过：

- 导出新 Engine 的命令配置：
  ```cmd
  yolo export model='Software/best.pt' format=engine dynamic=True device=0 batch=16 half=True
  ```
- 该导出极大地缓解了 PCIe 数据带宽与模型参数的负载压力；
- **分层化窗口选择策略**：结合引擎预测，优先选择含“Flight-control”飞控信号窗口；随后无差别保底最高置信度；末级则回退历史选择。保证了可视化追踪界面的绝对稳定。

### 3.4 模块业务解耦重命名
将所有配置流与组件命名中包含早期硬件直连含义的 "Receiver" 更名为 **"Slave Computer"** (下位机)，以此更精确地表述该模块对接的是独立运行的射频从机。

## 4. 关键逻辑错误与解决方案

### 4.1 错误一：inference_engine 中的 ValueError: could not broadcast input array
**现象**：
系统在初次启动建立连接时会立即崩溃，报错形如：could not broadcast input array from shape (129,20480) into shape (129,10240)。但断开设备重连后会奇迹般恢复正常。

**排查分析**：
由于共享内存 shm_waterfall 是以 MAX_WATERFALL_HEIGHT * MAX_TOTAL_FFT 静态最大申请预分配的。在瀑布图尚未到达指定历史深度（cnt < h 时启动缓存补全阶段）时，切片读取了整行 20480 的最大物理长度，但需要被赋值到的观测容器 waterfall_view 是基于应用端实际限制长度（如 10240）的。这就产生了尺寸不统一引发的 numpy broadcast 异常。
重连后之所以不报错，是因为填满缓存池后系统执行了 else 中的截断切片。

**解决方案**：
在 cnt < h 分支中，强制对共享缓冲环加上真实的截断参数限制 :self.waterfall_width。

### 4.2 错误二：Python UI脚本UTF-8不可读 (SyntaxError: unicode error/unmatched)
**现象**：
在 PowerShell 环境中执行自动代码替换后，尝试冷启动 main.py 会连续报出多个涉及 SyntaxError 以及 UI 面板乱码或编译无法通过（如找不到大括号映射匹配）的错误。

**排查分析**：
PowerShell 默认对重写流使用了 Windows-1252 (GBK/ANSI) 编码或者携带有 U+FEFF（BOM 头）的伪 UTF-8，破坏了 Python 文件开头的严格 utf-8 环境要求及内部 f-string 中的多括号解析器规范。

**解决方案**：
切入 .NET 底层方法重新覆写各层配置页面和主题调用相关文件，剥离有毒的 BOM 前缀，并强制要求采用系统级的纯 [System.Text.Encoding]::UTF8。

## 5. 本次改造涉及重构文件清单

- **Software/ipc.py**: 修改并扩增 shm_waterfall_ring，替代之前的 multiprocess.Queue 通信组件。
- **Software/receiver.py**: communication.py 的重命名与技术演进，合并原 1D DSP 处理并挂载共享内存。
- **Software/inference_engine.py**: data_process.py 的精简完全体，聚焦于单纯监控并零延时获取大数组的纯 GPU 张量变换池并实施算法批处理。
- **Software/state.py & Software/parameters.json**: 将通信协议命名从 "Receiver" 更新为正式的 "Slave Computer" 下位机控制面。
- **Software/main.py**: 全新引入与调配双守护子进程入口。
