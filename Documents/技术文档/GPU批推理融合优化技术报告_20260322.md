# 无线无人机检测系统技术报告（2026-03-22）

## 1. 报告目的

本文档详细记录今日围绕“数据处理与检测链路GPU化”的全部技术改造，覆盖以下目标：

- 在数据处理层引入完整的GPU加速路径。
- 用Numpy环形缓冲 + 指针重建替代deque。
- 合并数据处理与YOLO检测流程，尽量保持数据在GPU侧完成。
- 记录改造过程中遇到的逻辑问题、排查过程与解决方案。

---

## 2. 改造前问题概述

### 2.0 最初版本基线（重要）

在最初版本中，数据处理阶段的关键图像计算几乎全部由CPU完成，包含：

- 全局归一化（对整幅瀑布图进行min/max统计与归一化）
- 色彩映射（强度值到JET伪彩映射）
- 图像重排与显示前处理

这一阶段是早期最主要耗时来源之一，CPU占用高、单帧时延大，且会压缩后续检测推理的时间预算。
本次GPU化改造的核心出发点之一，就是把这部分“最重的图像计算”从CPU迁移到GPU。

### 2.1 链路瓶颈

但此链路又存在多次跨设备拷贝：

1. FFT数据处理后在CPU侧组装图像。
2. 图像上传GPU做色彩映射/检测。
3. 检测结果或图像再回传CPU用于共享内存和UI显示。

这会引入显著的PCIe开销，特别是大尺寸瀑布图场景。

补充说明：

- 在“CPU归一化 + CPU映射”的最初阶段，瓶颈主要是CPU计算本身。
- 在“部分GPU化但流程分裂”的中间阶段，瓶颈转移为GPU-CPU-GPU往返与跨进程传输。
- 因此最终方案需要同时解决“CPU重计算”和“跨设备拷贝”两类问题。

### 2.2 数据结构瓶颈

旧实现基于deque缓存瀑布图行数据，需要在显示或计算前做拼接/转换，造成额外的内存分配与复制开销。

### 2.3 架构耦合问题

检测子进程与数据处理子进程彼此串行依赖，导致：

- 需要额外共享内存桥接中间图像。
- 参数和状态同步链路更长。
- GPU计算阶段被拆碎，不利于整体吞吐。

## 3. 核心改造内容

### 3.0 从最初到当前的演进路径

本次优化并非一步到位，而是按以下路径演进：

1. 最初：CPU完成全局归一化 + 颜色映射 + 图像处理，整体耗时高。耗时主要表现在deque转为ndarray，全局归一化，颜色映射三个方面。
2. 第一阶段：引入Numpy环形缓冲，避免使用deque。
3. 第二阶段：归一化与JET映射迁移到GPU，降低CPU压力。
4. 第三阶段：进一步优化，减少processer和detector之间的两次CPU-GPU迁移，即合并DataProcess与YOLO检测，减少跨进程中间图传输。
5. 当前阶段：尝试批量并行推理并完善窗口选择与统计可观测性。

## 3.1 数据处理层：Numpy环形缓冲替代deque

改造位置：Software/data_process.py

### 3.1.1 新增/重构点

- 使用预分配数组构建环形缓冲：
  - waterfall_ring: 存储原始频谱行（环形写入）
  - waterfall_view: 存储重建后的连续视图
- 引入写指针与计数器：
  - ring_write_idx：下一次该写入的位置
  - ring_count：有效行数
- 重建逻辑封装为 _rebuild_waterfall_image。

### 3.1.2 实现价值

- 避免deque到ndarray的高频转换。
- 内存分配行为更加稳定（预分配 + 就地写入）。
- 时间复杂度和拷贝路径可控，便于后续GPU上传。

---

## 3.2 数据处理层：GPU色彩映射与图像生成（加速归一化与映射计算）

改造位置：Software/data_process.py

### 3.2.1 GPU流程

1. 将重建后的waterfall_array上传至GPU：
   - torch.from_numpy(...).to(device)
2. 在GPU做归一化：
   - aminmax求范围
   - (x - min)/(max - min)
3. 在GPU做JET查表映射：
   - jet_lut为GPU张量
   - 通过索引得到彩色图像 color_tensor

### 3.2.2 优化点

- 归一化与色彩映射完全GPU化。
- 减少CPU侧逐像素处理。

## 3.3 架构重构：合并数据处理与YOLO检测（减少GPU-CPU-GPU的时间）

改造文件：

- Software/algorithms.py
- Software/data_process.py
- Software/main.py
- Software/ipc.py

### 3.3.1 设计变化

- 移除独立的旧检测进程流程（扫描控制器主导的路径）。
- 在DataProcessor内部直接加载并调用BatchDroneDetector。
- 数据流改为：
  - FFT处理 -> GPU瀑布渲染 -> GPU窗口批检测 -> 仅回传被选中窗口到UI共享内存。

### 3.3.2 IPC重构

- 删除waterfall共享块（大体量中间图像不再跨进程传输）。
- 保留两类共享内存：
  - SHM_SPECTRUM
  - SHM_DETECTION（UI显示图）
- 新增detection_lock用于检测图写入同步。

### 3.3.3 主进程适配

- main.py中仅启动通信进程 + DataProcessor进程。
- 参数下发改为统一走dp_ctrl_q。
- scan_status做dict类型防护，避免UI状态更新异常。

## 3.4 批量推理能力与窗口选择逻辑

改造位置：Software/algorithms.py, Software/data_process.py

### 3.4.1 批量窗口切分

- 依据fft_length作为窗口宽度。

- 按max_batch_windows（默认16）截取可用窗口。

- 张量重排为批量格式后送入YOLO推理。

- YOLO导出：

  ```bash
  yolo export model='Software/best.pt' format=engine dynamic=True device=0 batch=16 half=True 
  ```

  相对于直接使用原始 `best.pt` 文件，上述导出命令的主要好处如下：

  1. 推理后端从PyTorch执行图切换为TensorRT Engine执行图，通常可显著降低推理延迟并提高吞吐。
  2. `half=True` 启用FP16推理，减少显存带宽压力和显存占用，通常可进一步提升FPS。
  3. `batch=16` 让引擎在导出时按批量场景优化，匹配本项目“多窗口并行推理”的目标。
  4. `dynamic=True` 允许引擎在一定范围内使用动态批次/形状（取决于导出与运行配置），更适合现场不同负载下的推理调度。
  5. 部署稳定性更高：离线编译后的Engine在目标GPU上运行路径更固定，减少运行时图优化开销与抖动。

  参数含义说明：

  - `model='Software/best.pt'`：以训练得到的PyTorch权重为导出源。
  - `format=engine`：导出为TensorRT Engine。
  - `dynamic=True`：启用动态维度支持（建议与推理侧输入策略一致）。
  - `device=0`：在0号GPU上构建引擎。
  - `batch=16`：导出时按16批量目标优化。
  - `half=True`：使用FP16精度。

  工程注意事项：

  - 如果导出的Engine仍然是固定 `max model size (1, 3, 512, 512)`，说明当前引擎未真正支持batch=16，需要重新导出或检查导出参数与版本兼容性。
  - `.pt` 文件更适合训练与调试；`.engine` 更适合在目标GPU上的高性能部署。

  

### 3.4.2 窗口选择策略优化

从“默认窗口0”调整为分层策略：

1. 优先选择Flight-control signal类别中置信度最高窗口。
2. 若无飞控目标，选择任意类别中置信度最高窗口。
3. 若无任何检测，保持上一次窗口（fallback_window = last_selected_window）。

该策略解决了界面长期显示第一个窗口的问题。

## 4. 关键逻辑错误与解决方案

## 4.1 错误一：TensorRT引擎固定batch=1导致批推理失败

### 现象

日志中出现大量报错（drone_detection.log）：

- input size torch.Size([16, 3, 512, 512]) not equal to max model size (1, 3, 512, 512)

### 原因

当前best.engine为固定batch=1的TensorRT引擎，不支持batch=16输入。

### 处理结论

- 代码侧批处理链路已搭建完成。
- 但要真正启用并行批推理，需要替换为支持动态batch或固定batch=16的TensorRT引擎。

### 后续建议

- 重新导出engine，至少支持batch维动态范围（如1~16）。
- 或导出固定batch=16引擎并配套推理参数。

---

## 4.2 错误二：颜色通道顺序不一致（BGR/RGB）

### 现象

怀疑窗口识别异常、目标窗口不符合预期（理论应在第10窗口）。

### 原因

- OpenCV与JET LUT输出是BGR语义。
- YOLO Tensor输入常见预期是RGB语义。

### 解决方案

- 在送入YOLO前执行BGR -> RGB通道翻转（torch.flip(..., dims=[-1])）。
- UI显示侧继续使用QImage.Format_BGR888，保持显示颜色正确。

---

## 4.3 错误三：窗口选择回退逻辑导致“总是第一个窗口”

### 现象

界面多数时间显示窗口1。

### 原因

无检测时回退到0号窗口，造成视觉上“黏住第一个窗口”。

### 解决方案

- 回退策略改为使用last_selected_window。
- 且在有检测时采用“最高置信度窗口”策略，减少抖动和误选。

---

## 4.4 错误四：scan_status结构不稳导致主线程更新风险

### 现象

状态更新阶段存在类型不确定风险。

### 解决方案

- main.py中增加scan_status的dict类型判断后再更新state。
